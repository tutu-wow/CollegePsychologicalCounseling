# 高校心理咨询平台

> WebSocket 在线咨询 · 量表在线测评与自动计分 · 咨询师排班预约与咨询评价 · 学生健康档案与跟踪备注 · 文章审核与论坛互动 · ECharts 运营看板与论坛词云

起因挺实在：学院心理中心的老师吐槽，学生想约一次咨询，得先跑一趟办公室问"这周谁有空"，量表还是纸质填、分数靠手算，测评结果随手夹进档案袋；等要做"这学期预约量多少、哪位咨询师评价最好"的统计，又得把袋子翻一遍。

这套系统就是冲着这个场景做的：**把量表、计分、排班、预约、咨询记录、评价、档案全部落到平台上，学生自己在手机上就能走完整条路**。做毕设答辩时，"量表总分为什么不能让前端传"和"预约时段是怎么校验的"这两段特别有讲头，比单纯写增删改查扎实。

## 一、项目简介

高校心理咨询平台采用前后端分离的 B/S 架构，由学生前台以及管理员、心理咨询师共用的管理端组成。系统以系统账号、学生、咨询师、心理测评量表、测评题目、测评记录、咨询预约、咨询评价、健康档案、档案备注、心理文章、放松小贴士、论坛帖子、评论点赞、公告、站内通知和操作日志为主要业务数据，围绕"学生注册、心理测评、预约咨询、咨询处理、评价反馈、档案沉淀、内容交流、运营统计"的校园心理服务场景组织功能。学生可完成测评、预约、阅读与论坛互动；咨询师可维护排班、处理本人预约、填写咨询记录并发布文章；管理员可维护平台基础数据、审核内容和查看运营情况。

## 五、核心实现

### 5.1 三角色账号体系、JWT 认证与端侧划分

系统将账号划分为管理员、学生和心理咨询师三类角色。学生通过前台完成测评、预约、内容浏览和个人服务管理；心理咨询师在管理端维护个人排班、查看本人预约、登记咨询小结并管理相关业务内容；管理员负责平台用户、咨询师、量表、文章、论坛、公告、轮播图和运营数据等全局管理。用户登录后，服务端在 JWT 中写入用户 ID 与角色信息；请求拦截器解析令牌后将当前用户保存到线程上下文，前端路由守卫根据角色将学生导向前台，将管理员和心理咨询师导向管理工作区。

### 5.2 心理测评量表配置、自动计分与结果解读

量表模块由量表分类、量表和题目组成。量表保存名称、描述、题目数量、预计用时、发布状态及审核信息；题目按量表关联并保存题型、选项、选项分值和排序。学生在前台选择量表并提交作答明细后，服务端读取题目选项，按已选选项累计总分，同时计算量表最高可能分。系统将量表名称、总分、满分和题目作答内容提交给 DeepSeek 接口生成结果解读与建议；接口未返回有效结果时，系统会根据得分比例生成默认解释和建议，并将作答详情、总分、解读与建议一并保存为测评记录。

这里有一个刻意的设计：**总分由服务端算，不接受前端传上来的分数**。前端传分的问题不在技术，在可信度——只要分数来自浏览器，就同时存在算错和被改两种可能，而且这两种情况事后无法区分。服务端读题目选项重新累计之后，测评记录里的分数是"可复现"的：拿作答明细重算一遍，结果必须一致。

### 5.3 咨询师排班、在线预约与预约状态流转

咨询师可维护以日期和时段为单位的排班信息。学生在咨询师列表和详情页了解咨询师资料、可用排班与预约方式，选择咨询日期、时段和咨询方式后提交预约。系统生成预约编号，并在创建前查询同一咨询师、日期和时段的已预约数量，用于预约时段校验。预约记录保存学生、咨询师、预约时间、咨询方式、问题简述、咨询地点和状态等信息；状态覆盖待确认、待咨询、咨询中、已完成、已取消和已拒绝。咨询师可确认、拒绝或完成本人预约，并在完成后填写咨询小结和建议；系统为咨询师工作台汇总当日预约、待确认、待咨询、本周完成量、累计完成量和平均评分等数据。

时段校验用的是**重新统计已预约数量**，而不是在排班表上挂一个"已约几人"的计数器。计数器看着省事，但只要出现取消、拒单、重复点击提交，数字就会和真实预约对不上，而且对不上以后没有任何办法自动恢复；重新统计每次都以预约表为准，慢了那么一点，但结果永远自洽。

### 5.4 咨询评价、学生健康档案与跟踪备注

系统以学生为中心维护健康档案，档案可关联负责咨询师，并保存档案基本信息。学生档案详情会汇集该学生的预约记录、测评记录和档案备注，使咨询过程中的主要信息能够在同一档案视图中查看。咨询完成后，学生可围绕预约提交评分和评价内容；评价记录关联预约、学生与咨询师，可供管理端查询。咨询师端可进入学生档案页面，查看与本人相关的学生信息、预约与测评情况，并新增或维护档案备注，为后续咨询提供连续的工作记录。

### 5.5 心理文章审核、放松贴士与收藏

内容服务包含心理文章、文章分类、放松小贴士和贴士分类。咨询师可以创建和编辑心理文章，文章记录作者、分类、标题、摘要、正文、封面、审核状态、审核时间和驳回原因等信息。管理员针对待审核文章执行通过或驳回操作：审核通过后文章转为已发布状态，审核驳回则记录原因；系统同时向文章作者发送相应的站内通知。学生端提供文章列表、文章详情、贴士列表和贴士详情页面，并支持通过收藏记录保存感兴趣的文章或贴士。

审核这里保留了**状态、审核时间、驳回原因三样一起写**的口径：只改状态不写原因，作者拿到"已驳回"三个字无从下手；只写原因不写时间，事后追溯"这条是谁什么时候处理的"就没有依据。

### 5.6 论坛交流、评论点赞与互动通知

论坛模块由帖子分类、帖子、点赞和评论组成。学生可按分类发布帖子，并在帖子详情中浏览内容、发表评论和进行点赞。帖子记录用户、分类、标题、内容、图片、浏览量、点赞数、评论数和置顶状态等信息。服务端在用户点赞前检查是否存在同一用户对同一帖子的点赞记录，避免重复点赞；点赞或取消点赞后重新统计帖子点赞数。发表评论后，系统重新统计评论数，并向帖子作者或被回复的评论用户发送站内通知。管理员可维护帖子分类、管理帖子和评论，并对帖子切换置顶状态。

点赞和评论数同样是**操作后重新统计**，而不是在前端做加减法。重复点击、网络重发都能产生两次"点赞成功"的假象，前端数字一旦跑偏，用户在页面上就能看出来；以点赞记录和评论表为准重新统计，数量始终等于明细条数。

### 5.7 WebSocket 在线咨询与消息记录

系统提供学生端和管理端在线咨询页面，并通过 WebSocket 建立消息通道。客户端连接 `/ws/chat` 后，服务端根据连接参数维护在线用户与会话的映射。用户发送消息时，服务端先调用消息服务保存聊天记录，再将消息推送给在线接收方，同时向发送方回传已保存的消息。连接关闭或传输出错后，对应会话会从在线映射中移除。该方式使学生与咨询师可以在平台内进行实时文字消息交流，同时保留已发送消息的业务记录。

顺序上有个要点：**先落库，再推送**。反过来做的话，推送成功了但落库失败，双方聊天界面上都有这句话，翻历史却找不到，这类"看得到、查不到"的消息最难排查；先落库再推送，最坏情况也只是需要刷新一次才看到。

### 5.8 公告、站内通知与操作日志

管理员可维护平台公告和轮播图，学生端提供公告列表与公告详情页面。站内通知覆盖预约状态变更、评论互动、留言回复、文章审核和系统通知等类型，用户可查看通知列表和未读数量，并执行单条或全部已读处理。系统通过 AOP 切面拦截新增、修改、删除、审核、预约、登录、注册等控制器操作，记录用户、操作类型、模块、执行结果和客户端 IP 等信息。

通知采用"事件发生即写入"的方式，而不是在页面上临时推导。原因很实际：用户想看的是"什么时候被告知了什么"，这是业务事实，需要和状态变更一起落库；如果靠页面实时拼，同一条通知的显示时间会随每次访问而变，未读数也没法稳定地维护。

### 5.9 运营数据看板与论坛词云

管理端数据看板提供平台概览、用户注册趋势、测评统计、预约统计、咨询师绩效、论坛统计和论坛词云等接口，前端使用 ECharts 展示统计结果。平台概览汇总学生、咨询师、量表、文章与预约等总量数据；注册趋势与测评、预约统计按时间维度聚合；咨询师绩效围绕预约处理量与评价情况展开；论坛统计覆盖帖子、评论与互动情况，并通过 Jieba 分词对帖子内容做词频统计，以词云形式呈现学生关注的话题分布。

看板的接口**按图表组织，而不是按表组织**：一个接口返回某张图需要的完整数据，前端拿到就能渲染。这样做的好处是统计口径收敛在服务端，同一个指标在概览、趋势和排行里不会出现三种算法；代价是接口不能复用，但这部分换来的是"报表和明细永远对得上"。

### 5.10 校园心理服务全流程

系统以学生注册和心理健康档案为起点，学生通过量表测评形成测评记录和结果解读，通过咨询师排班信息在线预约咨询服务；咨询师确认预约、开展咨询并填写咨询小结与建议，学生在咨询完成后提交评价。相关记录按学生归集到健康档案，咨询师可持续补充档案备注；心理文章、放松小贴士和论坛为学生提供日常心理调适与同伴交流入口；文章审核结果、预约状态变更和评论互动通过站内通知反馈给相关用户；关键操作写入日志，运营数据在看板中汇总呈现。管理员负责基础数据与内容审核，咨询师承担咨询服务与档案记录，学生完成测评、预约和反馈，共同构成可查询、可追溯、可统计的校园心理服务流程。

| 文件与统计 | Apache POI（Excel 导入导出）、Spring MultipartFile 文件上传、AOP 操作日志 |

## 八、适合谁

- 想做**场景贴切、故事好讲**的毕设：高校心理健康服务方向，答辩时从"学生约一次咨询要跑几趟"讲起，评委一听就懂
- 想体现**多角色协同**能力的同学：学生、心理咨询师、管理员三端分工明确，咨询师的工作台还按本人预约与评价收口数据
- 想在论文里写**量表与计分规则**的同学：题目选项分值、总分与满分计算、得分比例分段、AI 解读与兜底逻辑，是一节完整的算法说明
- 需要**状态机设计**落点的同学：预约六态流转加拒绝原因、文章审核两态加驳回原因，状态图好画、边界条件好写
- 想写**实时通信**的同学：WebSocket 会话映射、消息先落库再推送、连接异常清理，比"聊天窗口截图"更有内容
- 想在论文里写**大模型应用**的同学：量表名称、总分、满分与作答内容构成上下文，AI 生成解读与建议并落库复用
